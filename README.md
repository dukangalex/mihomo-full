# mihomo-full

> **Public template** — sample values only. Never commit real airport URLs, domains, UUIDs, passwords, or node secrets. Use **Use this template** / Fork, then fill secrets **only on your VPS**.

基于 **机场入口订阅 + VPS 自建落地节点** 生成完整 Mihomo 配置。核心设计是：**机场只作为前置入口，VPS 落地节点作为最终出口**；客户端只导入一个固定 HTTPS 订阅地址。

---

## 核心链式架构

```text
客户端
  │
  ▼
Mihomo
  │
  │ 国外业务
  ▼
落地优选出口 / 落地负载均衡 / 落地手动选择
  │
  │ dialer-proxy
  ▼
前置优选入口
  │
  ▼
机场订阅节点（仅入口）
  │
  ▼
VPS 自建落地节点（最终出口）
  │
  ▼
目标网站 / 服务
```

**必须理解：** `dialer-proxy` 是链式关系的关键。落地节点通过 `前置优选入口` 建立连接，因此“落地节点”不是简单地直接连接目标，而是由机场节点承载其上游连接。最终对外访问使用的是所选落地节点的出口。

### 节点职责

| 组件 | 职责 | 是否作为最终出口 |
|---|---|---|
| **前置优选入口** | 从机场订阅中选择入口节点，负责承载到 VPS 落地节点的连接 | 否 |
| **provider_exit / 落地优选出口** | 从 VPS 自建节点中选择最终落地节点 | 是 |
| **国外服务 / AI / 流媒体等功能组** | 调用落地出口策略组 | 不直接承担入口职责 |

## 落地节点选择：这是链式配置最重要的操作

本项目**不再按协议类型排除落地节点**。`generate.sh` 会把 v2ray-agent 的 clashMeta 目录中提取到的节点原样保留到落地候选池；不因为 VMess、VLESS、Reality、Hysteria2、TUIC、Trojan、Shadowsocks、WireGuard 等协议名称而武断删除。

### 正确的选择顺序

**第一步：确认整条链能通。**

```text
机场入口 → VPS 落地节点 → 目标
```

不能用“VPS 节点单独直连正常”代替链式测试。

**第二步：比较目标业务表现。**

重点观察：

- 首次连接时间
- 延迟与抖动
- 下载 / 上传速度
- 长连接稳定性
- 丢包与断流
- 视频、实时通信、UDP 等实际表现
- 高峰时段稳定性

**第三步：保留多个可用落地节点。**

`落地优选出口` 用于自动选择；`落地手动选择` 用于人工固定节点。建议保留至少两个经过实际链式验证的候选，避免单点故障。

### 入口与出口必须分开评价

不要把下面两个概念混为一谈：

```text
入口质量：客户端 → 机场 → VPS
出口质量：VPS → 目标服务
```

一个机场入口可能很快，但到某个 VPS 落地节点的链路很差；一个 VPS 落地节点也可能本身很好，但某个机场入口无法稳定承载它。

因此，**真正应该选的是“机场入口 + VPS 落地节点”的组合质量**，而不是只看其中一端。

### 协议兼容性说明

不同落地协议对 `dialer-proxy` 的中继环境要求可能不同。尤其 UDP 类协议或带特殊 TLS / 握手机制的协议，在某些机场入口下可能出现：

```text
节点单独直连正常
        ↓
经机场入口链式失败 / 不稳定
```

遇到这种情况，不要让生成器自动删除协议；应按以下顺序排查：

1. 换一个机场入口节点；
2. 再测试同一个 VPS 落地节点；
3. 若仍失败，再换 VPS 上另一个落地协议；
4. 检查 VPS 防火墙、端口和协议服务；
5. 最后检查生成后的 `provider_exit` 与 `dialer-proxy` 配置。

这样可以避免把“入口不兼容”误判成“落地节点失效”。

## 安装顺序

### 1. 准备 VPS 落地节点

本仓库不会安装 v2ray-agent，只读取其本地 clashMeta 节点文件。

### 2. 安装 mihomo-full

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/dukangalex/mihomo-full/main/install.sh)
```

按提示填写机场订阅、域名和 clashMeta 目录。机场订阅仅作为链式前置入口使用，并要求 HTTPS。

### 3. 配置 HTTPS 静态订阅

使用仓库中的 `nginx-example.conf`，然后执行：

```bash
nginx -t && systemctl reload nginx
```

客户端只导入安装器最后输出的固定 HTTPS 地址。

## 链式故障与安全边界

本项目的核心链路是：

```text
国外业务
  ↓
落地策略组
  ↓
provider_exit
  ↓
dialer-proxy = 前置优选入口
  ↓
机场入口
  ↓
VPS 落地
  ↓
目标
```

因此不要随意：

- 把 `provider_exit` 改成机场节点；
- 删除 `dialer-proxy`；
- 给国外业务组增加 DIRECT；
- 在落地失败时增加 DIRECT 作为“自动备用”。

如果机场入口全部失败，正确的安全行为应是**链式失败**，而不是让国外业务绕过机场直接连接。

## 安全原则

- 机场是**入口**，VPS 落地节点是**最终出口**。
- `dialer-proxy` 是链式关键，不应随意删除或改成 DIRECT。
- 落地节点不按协议类型武断筛选，实际可用性由完整链路测试决定。
- 用户界面不提供普通 DIRECT 作为国外业务出口。
- NTP 保持关闭，避免额外控制面流量。
- 真实订阅与生成物只存在 VPS，不提交公开仓库。
- 安装器使用固定 commit 下载核心脚本/模板，升级时应重新审核并更新 pin。

---

## 注意事项

1. 本项目的“链式”是 **机场入口 → VPS 落地 → 目标**。
2. `provider_exit` 的 `dialer-proxy` 是链式关键。
3. **所有落地节点都会保留**；某协议链式不稳定时，应通过更换入口或选择其他落地节点解决。
4. 选择落地节点时必须测试完整的“机场 → VPS → 目标”链路，而不是只测试 VPS 单节点直连。
5. 如果机场全部不可用，不能把落地节点当作 DIRECT 备用路径。
6. 生成后的 `full-config.yaml` 含真实机场订阅 URL，严禁上传公开仓库。
