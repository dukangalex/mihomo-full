# Mihomo-Full 公共行为策略

本文件定义链式主配置与机场覆盖模式之间的**公共行为底线**。两种模式允许保留各自的节点/策略组实现，但不得因为实现方式不同而产生意外的安全分歧。

## 1. 两种模式

- **链式模式**：机场前置入口 → 自建 VPS 落地 → 目标。
- **纯机场模式**：机场节点 → 目标。
- VPS 落地、`dialer-proxy`、落地节点选择属于链式专属能力，不要求出现在机场覆盖脚本中。
- **两种模式均不按 VMess、Shadowsocks、Trojan、VLESS、Hysteria、TUIC 等协议名称自动排除节点。** 协议名称本身不足以判断实际安全性；节点是否可信还取决于服务端配置、传输层、加密方式和节点来源。

## 2. 广告拦截

默认策略：`REJECT-DROP`。

主配置与机场覆盖脚本均保留一个“广告拦截”策略组：

- `REJECT-DROP`：默认值，正常使用。
- `DIRECT`：**仅在用户主动需要时使用**。

为什么保留 DIRECT：部分免费资讯、视频、下载、工具或其他网站依赖广告收入维持运营。广告被拦截后，可能出现页面无法加载、播放失败、验证码/登录异常或功能缺失。

**建议：**只有确认某个网站因广告拦截导致功能异常，并且愿意接受该网站广告请求直连时，才临时切换为 DIRECT。不要把 DIRECT 当作全局关闭广告拦截的常规开关。

钓鱼/恶意域名规则不属于普通广告规则，仍保持强制拦截，不提供 DIRECT 例外。

## 3. 远控工具

远控/内网穿透工具（如 Tailscale、AnyDesk、RustDesk、frp 等）默认使用当前策略，并保留：

- `落地优选出口`（链式模式）或对应机场代理出口；
- `DIRECT`。

`DIRECT` 是**用户主动启用的例外**，不是默认旁路。部分远控工具的 P2P 打洞、局域网发现、中继或厂商安全机制可能与代理/TUN 路由冲突；遇到明确的连接问题时，再尝试 DIRECT。

## 4. 私有网络

私有网络保持底层 `DIRECT`，但不单独暴露一个“私有网络直连”用户策略组。

原因：RFC1918/localhost/link-local/ULA 等地址属于本机或局域网拓扑，访问 NAS、路由器管理页、打印机、局域网服务等不应绕到机场/VPS。把它做成用户可切换的代理策略反而容易破坏本地网络。

因此：

- 私有地址 → 底层 DIRECT；
- 不作为“全局直连”按钮暴露给用户；
- 继续通过私有 IP 规则集/内置规则处理。

## 5. 国内服务

国内服务继续底层 DIRECT，不新增一个“国内服务 DIRECT”用户按钮。

判断优先级采用：

1. 国内域名规则集；
2. 国内服务补充域名规则；
3. `cn-ip` / GEOIP CN 等 IP 规则；
4. 最终未知流量仍进入代理出口。

原因：域名所在国家、CDN 实际 IP 和服务依赖的第三方域名并不总是一致。单纯用 GEOIP 判定会产生误判；而把“国内直连”做成用户开关又没有必要。

核心原则仍然是：**未知目标不得因为无法准确判断而获得境外直连机会。**

## 6. UI 原则

用户界面不显示一个通用的 `DIRECT` 全局按钮。

允许出现 DIRECT 的场景只限于明确的、局部的例外策略，例如：

- 广告拦截 → `REJECT-DROP / DIRECT`；
- 远控工具 → `REJECT-DROP / 代理 / DIRECT`。

私有网络和国内服务的 DIRECT 保留在底层规则中。

机场覆盖脚本原有的地区、自动选择、负载均衡等策略组属于机场模式的用户体验，应继续保留，不因公共行为同步而删除。

## 7. 维护原则

修改 `template.yaml` 后，应同步检查：

- `airport_overwrite.js`
- `generate.sh`
- Telegram 管理入口
- README/文档

不能只修改其中一个文件后宣称两种模式行为一致。

同步工具必须遵守：

- 同步公共行为；
- 不覆盖机场模式既有策略组布局；
- 不删除广告拦截/远控的 DIRECT 例外；
- 不进行协议名称过滤；
- 不把链式 VPS/dialer-proxy 能力错误注入纯机场模式。
